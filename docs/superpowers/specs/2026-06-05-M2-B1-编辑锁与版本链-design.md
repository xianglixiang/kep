# M2-B1 编辑锁 + 版本链 Design

- 日期：2026-06-05
- 类型：子系统 spec（M2-A 基础上增量）
- 状态：已评审通过

## 0. 范围

M2-B1 落地两个子能力：**编辑锁**（防止多人同时改同一 knowledge）+ **版本链**（再上传 docx 产生 v2、v3...）。

**不在 M2-B1 范围**：diff、回滚（**M2-B2**）；在线富文本编辑器（**M2-C**）。

完成判据：
- 单人可拿锁 → 上传 v2 → 释放锁 全流程跑通
- 锁被他人持有时：第二人拿锁得 409；持锁人上传 v2 正常；第二人尝试上传 v2 得 403
- 锁过期（30 min）后：第二人可拿
- 列表版本接口返回所有历史版本，current_version_id 指向最新

## 1. 已确认参数

| 维度 | 决策 |
|------|------|
| 锁抢占 | 可过期，30 min TTL；过期后任何有 WRITE 者可抢 |
| 版本号机制 | MAX(version_no) + 1，插入时计算 |
| 上传后锁是否自动释放 | 否，锁保持；用户手动 DELETE /lock 释放 |
| 编辑触发动作 | 上传新 docx（主路径） + 预留 PUT HTML 入口（M2-C 预备，M2-B1 给 501 桩） |

## 2. 数据模型（V4 迁移）

```sql
CREATE TABLE edit_lock (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id     VARCHAR(64)  NOT NULL,
    knowledge_id  BIGINT       NOT NULL,
    holder_id     BIGINT       NOT NULL,
    acquired_at   TIMESTAMPTZ  NOT NULL DEFAULT now(),
    expires_at    TIMESTAMPTZ  NOT NULL,        -- acquired_at + 30 min
    CONSTRAINT uk_edit_lock_knowledge UNIQUE (knowledge_id)  -- 同一 knowledge 同时刻一锁
);
CREATE INDEX idx_edit_lock_tenant_expires ON edit_lock (tenant_id, expires_at);
```

> 一条 knowledge 一把锁（UNIQUE 约束）。M0 spec 是 `edit_lock.knowledge_id UNIQUE`，沿用。

## 3. 业务规则

### 3.1 锁获取（POST /api/knowledge/{id}/lock）

```
Input:  (none — just user from SecurityContext)
Auth:   check(userId, knowledge.catalogNodeId, WRITE)

Logic:
  1. 查 knowledge → catalogNodeId
  2. check(userId, catalogNodeId, WRITE)  // M1 PermissionChecker
  3. SELECT * FROM edit_lock WHERE knowledge_id = ? AND tenant_id = ?
     - 不存在 → INSERT 新锁（expires_at = now() + 30min）→ 返回 200 + lock 信息
     - 存在但 expires_at < now() → UPDATE holder=current_user, acquired_at=now(), expires_at=now()+30min → 200
     - 存在且未过期 + holder != current_user → 409 Conflict
     - 存在且未过期 + holder == current_user → idempotent return 200（视为刷新 TTL）
     - 存在且未过期 + holder == current_user + 加 ?force=true → 允许（保留现状）
```

> 简化：M2-B1 不实现 `?force=true` 抢占。过期才能被抢。

### 3.2 锁释放（DELETE /api/knowledge/{id}/lock）

```
Auth: 无权限检查（释放自己的锁）
Logic:
  1. SELECT * FROM edit_lock WHERE knowledge_id = ?
     - 不存在 → 404
     - holder_id != current_user → 403
     - holder_id == current_user → DELETE → 200
```

### 3.3 新版本上传（POST /api/knowledge/{id}/versions）

```
Input:  multipart (file=docx, title 可选)
Auth:
  - check(userId, knowledge.catalogNodeId, WRITE)
  - 必须有 lock 且 lock.holder == current_user
Logic:
  1. check WRITE
  2. 查 lock: lock.holder_id == current_user
     - 不满足 → 403 Forbidden ("请先获取编辑锁")
  3. POI 转换 docx → HTML（复用 M2-A PoiDocxToHtml）
  4. 解析 title（DefaultTitleExtractor 或 request.title）
  5. 找 MAX(version_no)：SELECT MAX(version_no) FROM knowledge_version WHERE knowledge_id = ? AND tenant_id = ?
     new_no = max + 1（若不存在则 1）
  6. 上传到 OSS：key = "tenant-{tid}/knowledge/{knowledgeId}/v{new_no}/original.docx"
  7. INSERT knowledge_version（version_no=new_no, change_type='UPDATE', parent_version_id=currentVersion.id）
  8. UPDATE knowledge SET current_version_id = new.id, updated_at=now()
  9. 锁保持（不自动释放）
  10. 返回 KnowledgeView + 新版本号
```

### 3.4 PUT HTML 入口（M2-C 预备，M2-B1 桩）

```
PUT /api/knowledge/{id}/content
Body: text/html (raw HTML)
Response: 501 Not Implemented + JSON {"code":"NOT_IMPLEMENTED", "message":"M2-C 即将支持"}
```

## 5. 关键设计取舍

- **锁与 knowledge 1:1**（UNIQUE knowledge_id），不需要锁表或分布式锁。同一 knowledge 同时刻只一人。
- **过期即失效**：30 min 后任何 WRITE 者可拿。M2-B2 可加 `?force=true` 抢占参数。
- **上传 v2 后锁保持**：用户可连续上传 v3/v4（编辑会话），手动 DELETE /lock 释放。
- **MAX+1 计算**：在事务内 `SELECT MAX(version_no)` + INSERT，简单可靠。低并发下不会冲突（持锁是排他的）。
- **PUT HTML 桩 501**：M2-C 富文本编辑器落地时直接接续；M2-B1 不实现但留接口。
- **不在 M2-A 的 knowledge_version 表加 parent_version_id 外键**：M0 schema 已有 parent_version_id 列，M2-B1 直接填（M2-A CREATE 时是 NULL，M2-B1 UPDATE 时填上一 current id）。
