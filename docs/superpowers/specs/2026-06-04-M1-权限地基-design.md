# M1 权限地基 Design

- 日期：2026-06-04
- 类型：子系统 spec（在总体架构 `2026-06-01-企业知识管理系统-总体架构-design.md` §4 范围内细化）
- 状态：已评审通过

## 0. 范围

替换 M0 的 `AllowAllPermissionChecker` 桩实现，落地三层鉴权：

1. **租户隔离**（沿用 M0 的 `@TenantId` + `TenantContext`，已就位）
2. **目录/知识 ACL 就近优先**（DENY 覆盖 GRANT，含单知识粒度）
3. **读/写分离**（WRITE 蕴含 READ）

完成判据（可演示）：
- 不同租户互不可见
- 目录/单知识 ACL 的"加人/减人/读写分离"完整可演示
- 业务服务（catalog、review）真实接入鉴权

## 1. 已确认参数

| 维度 | 决策 |
|------|------|
| 主体类型 | 组织架构 + 个人双主体（`subject_type = ORG_UNIT \| USER`） |
| 审核者来源 | 复用 `org_unit` 作为审核者组 |
| ACL 表设计 | 单表 + `subject_type` |
| 算法 | 默认拒绝 + 就近优先（DENY 覆盖 GRANT）+ WRITE 蕴含 READ + 物化路径 |
| 边界 | `catalog_node.path` 回填、`org_unit.path` 物化、ACL 联合索引、`review_request` M1 落 schema |
| 临时鉴权 | `X-User-Id` 头（M2+ 替换为真实 Spring Security） |

## 2. 数据模型

### 新增 / 修改表

```
-- 用户（每租户独立）
CREATE TABLE app_user (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id     VARCHAR(64)  NOT NULL,
    username      VARCHAR(200) NOT NULL,
    display_name  VARCHAR(200),
    status        VARCHAR(20)  NOT NULL DEFAULT 'ACTIVE',
    created_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),
    UNIQUE (tenant_id, username)
);
CREATE INDEX idx_app_user_tenant ON app_user (tenant_id);

-- 组织（已有物化路径）
CREATE TABLE org_unit (
    id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id    VARCHAR(64)   NOT NULL,
    parent_id    BIGINT,
    name         VARCHAR(200)  NOT NULL,
    path         VARCHAR(1024) NOT NULL DEFAULT '/',  -- M1 新增：物化路径 /1/4/9/
    created_at   TIMESTAMPTZ   NOT NULL DEFAULT now()
);
CREATE INDEX idx_org_unit_tenant_path ON org_unit (tenant_id, path);

-- 用户∈组织
CREATE TABLE user_org (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id   VARCHAR(64) NOT NULL,
    user_id     BIGINT       NOT NULL,
    org_unit_id BIGINT       NOT NULL,
    UNIQUE (user_id, org_unit_id)
);
CREATE INDEX idx_user_org_user ON user_org (tenant_id, user_id);

-- ACL（核心）
CREATE TABLE acl (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id     VARCHAR(64)  NOT NULL,
    resource_type VARCHAR(40)  NOT NULL,            -- M1: CATALOG_NODE
    resource_id   BIGINT       NOT NULL,
    subject_type  VARCHAR(20)  NOT NULL,            -- USER | ORG_UNIT
    subject_id    BIGINT       NOT NULL,
    permission    VARCHAR(20)  NOT NULL,            -- READ | WRITE
    effect        VARCHAR(10)  NOT NULL DEFAULT 'GRANT',  -- GRANT | DENY
    created_at    TIMESTAMPTZ  NOT NULL DEFAULT now()
);
-- 判定查询模式：resource_id IN (...) AND (subject_type, subject_id) IN (...)
CREATE INDEX idx_acl_query ON acl (tenant_id, resource_id, subject_type, subject_id);

-- catalog_node 加 path（M0 表已存在，V2 加列 + 回填）
ALTER TABLE catalog_node ADD COLUMN path VARCHAR(1024) NOT NULL DEFAULT '/';
CREATE INDEX idx_catalog_node_tenant_path ON catalog_node (tenant_id, path);

-- 审核（M1 落 schema，状态机 M4 补）
CREATE TABLE review_request (
    id                    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id             VARCHAR(64)  NOT NULL,
    knowledge_id          BIGINT       NOT NULL,   -- M1 阶段等同 catalog_node_id
    version_id            BIGINT,                  -- M2 引入 knowledge_version 表后外键化
    status                VARCHAR(20)  NOT NULL DEFAULT 'PENDING',  -- PENDING|M4 扩展
    submitter_id          BIGINT       NOT NULL,
    reviewer_subject_type VARCHAR(20)  NOT NULL,   -- ORG_UNIT | USER
    reviewer_subject_id   BIGINT       NOT NULL,
    decided_at            TIMESTAMPTZ,
    opinion               TEXT,
    created_at            TIMESTAMPTZ  NOT NULL DEFAULT now()
);
CREATE INDEX idx_review_tenant_status ON review_request (tenant_id, status);
```

### M0 → M1 迁移策略

- V2 迁移脚本：
  - 给 `catalog_node` 加 `path` 列（默认值 `/`）
  - 给 `org_unit` 加 `path` 列
  - 回填两表的 `path`：按 `id` 升序，根节点 `path='/{id}/'`，子节点 `path = parent.path || id || '/'`
  - 创建新表（`app_user` / `user_org` / `acl` / `review_request`）

## 3. 判定算法

### 三层流水线

```
请求 → [第①层 租户隔离] → [第②层 目录 ACL 就近优先] → [第③层 读/写区分] → 放行/拒绝
         ↑                   ↑                            ↑
         框架已就位           主体解析 + 路径祖先 + 命中   WRITE 蕴含 READ
         (M0 @TenantId)      + 就近优先 + DENY 覆盖
```

`ThreeTierPermissionChecker.check(userId, catalogNodeId, requiredPermission)`：

```
1. tenant ← TenantContext.get();  若 null 抛 AccessDenied

2. subjects ← { (USER, userId) }
              ∪ { (ORG_UNIT, ouId) for ouId in userOrgPort.ancestorOrgIds(userId) }

3. ancestorIds ← catalogPathPort.ancestorIds(catalogNodeId)   -- 由 path 解析得 id 列表
                  // 例如 path='/1/4/9/' → [1, 4, 9]

4. hits ← aclPort.findHits(tenant, ancestorIds, subjects, requiredPermission)
   -- 一次 SQL，permission 已压到 WHERE 条件

5. 按 distance 升序遍历 hits（distance = ancestorIds.length - indexOf(resourceId)）
   用 (subjectType, subjectId) 作 key，锁定首次出现的 effect（就近优先）
   - 任一 key 锁定为 DENY → 拒绝
   - 至少一个 key 锁定为 GRANT 且无 DENY → 放行
   - 无任何命中 → 拒绝（deny-by-default）
```

### 关键不变量

- **业务代码无法绕过**——所有写路径只经 `PermissionChecker.check(...)`，catalog/review 服务不直接调 repository 写数据而不 check
- **deny-by-default**：第 5 步无命中即拒绝
- **WRITE 蕴含 READ**：服务层不做"先查 WRITE 失败再查 READ"的二次探测；调用方传哪个 permission，算法就只判哪个
- **就近优先在算法层**，单表 `effect` 列即可

### 性能

整条判定 **3 个 SQL 调用**（含租户上下文）：
- 步骤 2：`SELECT id FROM org_unit WHERE path @> ?` 或 path-LIKE 一次拉用户所有祖先 org
- 步骤 3：`SELECT id FROM catalog_node WHERE path = ?` 一次拉目标节点所有祖先 id
- 步骤 4：IN-list 一次查全部 ACL 命中

无 N+1。性能基准在 `PermissionCheckerIT` 验证。

## 4. 集成点

### `SecurityContext` 扩展

- `SecurityContext.setCurrentUserId(Long)` / `getCurrentUserId()`（ThreadLocal）
- `SecurityFilter` 替代 M0 的 `TenantFilter`，从 `X-User-Id` + `X-Tenant-Id` 两个头读取并填充 `SecurityContext`
- `TenantContext` 保留并由 `SecurityFilter` 顺带填充（兼容 M0 已用 TenantContext 的代码）

### 各服务接入

**catalog.CatalogService**（M0 已存在，M1 改造 + 新增）

| 方法 | M1 行为 | 鉴权 |
|------|---------|------|
| `create(userId, req)` | 强制 `parentId != null`（根由引导脚本预置）→ `check(userId, parentId, WRITE)` → 存（用 `parent.path + newId` 算 path） | WRITE on parent |
| `listChildren(userId, parentId)` | `check(userId, parentId, READ)` → 拉直接子节点 → 过滤掉 user 不可 READ 的子节点 | READ on parent + each child |
| `bootstrapRoot(tenantId, name)` | 创建根 `catalog_node`（path=`/1/`）并配全租户 READ ACL | 系统调用，无需 user |

**review.ReviewService**（M1 新增骨架）

| 方法 | M1 行为 |
|------|---------|
| `submit(userId, knowledgeId, versionId, reviewerSubject)` | `check(userId, knowledgeId, WRITE)` → 校验 reviewer 存在 → 插 `review_request`（status='PENDING'） |
| `decide(userId, reviewId, approved, opinion)` | 读 review_request → 校验 userId 匹配 reviewer_subject → `check(userId, knowledgeId, WRITE)` → 更新 decided_at/opinion（**不切换 status**，M4 补） |

> `review_request.knowledge_id` 在 M1 阶段按 `catalog_node_id` 使用；M2 引入真正的 `knowledge` 表后该列变成外键，service 签名不变。

**document.DocumentApi** —— M1 不动，M2 落上传/编辑锁时再调 check。

### 错误信号

- `AccessDeniedException`（Spring Security 标准）→ `GlobalExceptionHandler` 映射为 `ApiResponse.error("FORBIDDEN", "无权访问")` HTTP 403
- 资源不存在 → `BusinessException(NOT_FOUND, "知识不存在")` HTTP 404
- 业务校验失败 → `BusinessException(BAD_REQUEST, ...)` HTTP 400

### 事务边界

- check 在事务**内**调用——避免长事务期间 ACL 被改导致 TOCTOU。M1 不在 service 层做 ACL 缓存（缓存留后期性能优化）。

## 5. 端口切分（让算法可纯函数测）

`ThreeTierPermissionChecker` 不直接依赖 JPA 仓储，而是依赖 3 个内部端口：

```java
interface UserOrgPort { Set<Long> ancestorOrgIds(long userId); }
interface CatalogPathPort { List<Long> ancestorIds(long catalogNodeId); }
interface AclPort {
    List<AclRow> findHits(long tenantId, Collection<Long> resourceIds,
                          Set<Subject> subjects, Permission perm);
}
```

- 生产实现：`JpaUserOrgPort` / `JpaCatalogPathPort` / `JpaAclPort`（`@Profile("!local-mock")`）
- 测试实现：`InMemoryAuthPort`（一个类同时实现 3 个接口，`@Profile("local-mock")`），单测直接 `new` 它灌数据，**零 Spring 零 DB**

## 6. 测试策略

### 层 1：算法表驱动单测（快速，零 DB）

`ThreeTierPermissionCheckerTest` 用 JUnit 5 `@ParameterizedTest` + `@MethodSource` 喂数据。

覆盖矩阵（至少 12 用例）：

| # | 场景 | 预期 |
|---|------|------|
| 1 | 无任何 ACL，请求 READ | 拒绝（deny-by-default） |
| 2 | user 直属 org 在 /产品 有 READ GRANT | 通过 |
| 3 | user 父 org（祖先）在 /产品 有 READ GRANT | 通过（继承） |
| 4 | user 在 /产品 有 READ GRANT，在 /产品/子 有 READ DENY | 拒绝（子 DENY 覆盖） |
| 5 | user 在 /产品/子 有 READ DENY，/产品 有 READ GRANT | 拒绝（就近 DENY 覆盖） |
| 6 | user 在 /产品 有 WRITE GRANT，请求 READ | 通过（WRITE 蕴含 READ） |
| 7 | user 在 /产品 有 READ GRANT，请求 WRITE | 拒绝（READ 不蕴含 WRITE） |
| 8 | 跨租户 | 拒绝 |
| 9 | 同一资源同一权限同一主体：WRITE GRANT + WRITE DENY | 拒绝（DENY 胜） |
| 10 | 多人授权合并：user 在 /子 READ GRANT + user 个人 READ DENY | 拒绝（同一主体就近优先） |
| 11 | 叶子知识 DENY：知识节点自身有 user READ DENY，目录无 ACL | 拒绝 |
| 12 | 多个 org 主体授权合并：org1 GRANT + org2 DENY（不同主体） | 放行 + 拒绝**合并**——任一主体 DENY 即拒 |

### 层 2：端到端 IT（Testcontainers，集成）

`CatalogPermissionIT` 灌 Flyway 种子数据：
- 1 个 tenant、3 个 org（产品部 → 子组 1/子组 2）、4 个 user（含跨组织归属）、6 条 ACL、深度 3 的 catalog_node 树

测试走 HTTP（`MockMvc` + `X-User-Id` 头），断言：
- `POST /api/catalog/nodes` 在 WRITE 不足时返回 403
- `GET /api/catalog/nodes?parentId=X` 过滤掉不可见子节点
- 跨租户的 user 头一律 403

### 层 3：算法真实接线 IT

`PermissionCheckerIT`，`@Autowired PermissionChecker`（生产实现），不通过 HTTP，直接调方法，验证：
- JPA ports 正确加载 user_org 链
- JPA ports 正确解析 path
- 就近优先在 SQL 拉取 + 算法层都正确
- 性能基准：3 个 SQL 调用（用 Hibernate Statistics 断言 SQL count）

### 回归

- 快速层（默认 `./mvnw test`）：M0 8 + M1 算法表驱动 12+ + 端口单测
- 集成层（`./mvnw test -Pit`）：M0 11 + M1 的 `CatalogPermissionIT` + `PermissionCheckerIT`

## 7. 不在 M1 范围

- 审核状态机（PENDING→APPROVED/REJECTED/WITHDRAWN、消息通知、超时）—— M4
- 真实 Spring Security 接入（替换 `X-User-Id` 头）—— M2+ 早期
- catalog 树的全树递归可见性查询 —— M3 知识地图
- ACL 管理端 API（CRUD） —— M2+
