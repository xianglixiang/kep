# M3 知识地图 Design

- 日期：2026-06-05
- 类型：子系统 spec（catalog 模块的对外接口，叠加 M0 数据模型 + M1 鉴权 + M2-A 知识存储）
- 状态：已评审通过

## 0. 范围

M3 落地 **4 个知识地图接口**：目录树、列表、详情（复用 M2-A）、面包屑。核心是**子树可见性**：user 只看见自己有 READ 权限的目录节点与知识。

完成判据：
- 树接口返回嵌套 JSON，过滤掉无 READ 权限的节点
- 列表接口支持 4 个过滤维度 + 分页
- 详情接口复用 M2-A 的 GET /api/knowledge/{id}
- 面包屑接口返回从根到当前节点的路径

## 1. 已确认参数

| 维度 | 决策 |
|------|------|
| 范围 | 全量：树 + 列表 + 详情 + 面包屑 + 过滤 |
| 子树可见性 | 不可读节点隐藏（user 看树时无感） |
| 树响应形式 | 嵌套 JSON（每节点含 children） |
| 列表过滤 | 4 维度：catalog_node_id（主）、doc_type、status、title 关键字 |

## 2. 数据模型

**无新表**。M0 catalog_node（path 物化）+ M1 acl + M2-A knowledge/knowledge_version 全在。

**新增索引**（V5 迁移）：
```sql
-- 树遍历按 parent_id 全扫一次，索引已有（V1）
-- 知识列表按 node_id+status 过滤，索引已有（V3 idx_knowledge_tenant_node + idx_knowledge_tenant_status）
-- 唯一新增：title 模糊搜索
CREATE INDEX idx_knowledge_tenant_title ON knowledge (tenant_id, lower(title));
```

> 注：Postgres `lower(title)` 索引支持 `WHERE lower(title) LIKE 'foo%'` 的前模糊查询。完全匹配用 `=` 即可。

## 3. API

### 3.1 GET /api/catalog/tree?rootId={可选}

```
Auth: 任意登录用户
Returns: 200 JSON
  {
    "rootId": 1,
    "tree": [
      {
        "id": 1, "name": "产品", "nodeType": "FOLDER", "path": "/1/",
        "knowledgeCount": 3,
        "children": [
          { "id": 4, "name": "接口规范", "nodeType": "FOLDER", "knowledgeCount": 1, "children": [] }
        ]
      }
    ]
  }
```

- `rootId` 缺省=1（业务约定：tenant 的根节点 id=1）
- 树包含 user 有 READ 权限的所有 ancestor + 当前子树
- 空节点（无 knowledge 且无有权限的子节点）也保留在响应中（让 user 知道节点存在）
- `knowledgeCount` 是该节点**直接**子知识数（不含子节点）

### 3.2 GET /api/catalog/knowledge?nodeId=&docType=&status=&q=&page=&size=

```
Auth: check(userId, nodeId, READ)
Query: 必填 nodeId; 可选 docType/status/q/page(default 0)/size(default 20, max 100)
Returns: 200 JSON
  {
    "page": 0, "size": 20, "total": 42,
    "items": [
      { "id": 1, "title": "...", "docType": "WORD", "status": "PUBLISHED",
        "currentVersionNo": 3, "createdAt": "...",
        "currentVersionId": 12 }   // 前端按 id 调详情接口拿内容
    ]
  }
```

- 必填 nodeId（前端从 tree 选节点时拿）
- `q` 走 `lower(title) LIKE 'pattern%'`（前模糊）。后端自动加 `%`
- 跨租户自动 404（`@TenantId` 过滤）

### 3.3 GET /api/catalog/breadcrumb?nodeId=N

```
Auth: 任意（即使无 READ 也允许看路径；详情接口才 403/404）
Returns: 200 JSON
  {
    "nodeId": 4,
    "path": [
      { "id": 1, "name": "产品" },
      { "id": 4, "name": "接口规范" }
    ]
  }
```

- 走 `catalog_node.path` 物化路径拆 id 列表 → JOIN 一次查所有 name
- 不检查 READ（面包屑是导航信息，不是数据访问）

### 3.4 GET /api/knowledge/{id} —— 复用 M2-A

M3 不新增，复用 M2-A 的 GET /api/knowledge/{id}（含 currentVersion.html）。

## 4. 集成点

### 4.1 新增 `com.kep.catalog.KnowledgeQueryService`

不放在 DocumentService（属 document 模块），新建 `KnowledgeQueryService` 在 **catalog 模块**（catalog 已是 OPEN 边界外的独立模块，但 allowedDependencies 含 shared/document/permission）。依赖：
- KnowledgeRepository（document 模块）
- KnowledgeVersionRepository
- CatalogNodeRepository
- PermissionChecker
- AclRepository（如需）

> **等等**：AclRepository 当前是 JpaAclPort 包私有的，catalog 模块无法直接注入。改成在 spec 里**把 AclRepository 升级为 @ApplicationModule 暴露的包外 API**（加 `@NamedInterface("api")` 之类）— 或更简单：catalog 通过 PermissionChecker 间接做可见性查（PermissionChecker.hasRead(...) 即可）。

**简化**：catalog 通过 PermissionChecker 间接查权限。不直接读 AclRepository。

### 4.2 树可见性算法

```
Input:  userId, rootId
Logic:
  1. 一次性 SELECT * FROM catalog_node WHERE tenant_id = ?  （拿所有节点 — 假设树 KB 级，全扫）
  2. 一次性 SELECT 用户的祖先 orgs（UserOrgPort.ancestorOrgIds） + (USER, userId)
  3. SELECT * FROM acl WHERE tenant_id=? AND resource_type='CATALOG_NODE' AND permission='READ'
     AND subject_id IN (userId + ancestor orgs)
     — 拿到 user 有 READ 权限的所有节点 id 集合
  4. 树以 rootId 为根递归向下：
     - 节点的 read_set ⊇ 该节点本身或某祖先有 READ → 保留
     - 子节点同理递归
     - 没有任何子被保留的空节点也保留（让 user 知道有这节点但没权限）
  5. 拼嵌套 JSON 返回
```

> **简化**："用户对节点有 READ" 等价于"用户对节点或某祖先有 READ ACL"。算法通过"祖先路径节点"判断。

时间复杂度：O(N) SQL + O(N) 内存（N=树节点数），对千节点级树毫秒级。M3+ 万节点级再优化（lazy 加载）。

### 4.3 列表 + 过滤 + 分页

`KnowledgeRepository.findByXxx` 多种 query method 组合 + Specification 动态拼条件。

简化方案：**只支持固定 3 种组合 query method**（spec 写明）：
- `findByTenantIdAndCatalogNodeIdOrderByCreatedAtDesc(tenant, nodeId, pageable)` — 主路径
- `findByTenantIdAndCatalogNodeIdAndDocTypeOrderByCreatedAtDesc(tenant, nodeId, docType, pageable)` — 含 doc_type 过滤
- `findByTenantIdAndCatalogNodeIdAndStatusOrderByCreatedAtDesc(tenant, nodeId, status, pageable)` — 含 status 过滤
- `findByTenantIdAndCatalogNodeIdAndDocTypeAndStatusOrderByCreatedAtDesc(...)` — 三者都含
- `q` 走 `lower(title) LIKE 'q%'` —— 用 4 个 query method 的任一个 + Specification 拼 q

> 注：少用 Specification（避免 Criteria API 复杂度）。如果 4 个 method 覆盖 90% 场景，剩下 10% 用 like 走 SQL native。

### 4.4 面包屑算法

走 `catalog_node.path = '/1/4/9/'` 物化路径：
1. 拆 path 得 id 列表 [1, 4, 9]
2. `SELECT id, name FROM catalog_node WHERE id IN (1, 4, 9) ORDER BY position(path)` —— 用 `array_position(...)` 或程序排
3. 返回有序列表

不检查 READ（user 知道节点存在但不能进，UX 一致）。

### 4.5 catalog 端点

新增 `com.kep.catalog.CatalogController`：
- `GET /api/catalog/tree`
- `GET /api/catalog/knowledge`
- `GET /api/catalog/breadcrumb`

> 注：现有 `CatalogController`（M0 引入）只管理 CRUD。M3 加查询端点 — 是新增 method 还是新 controller？M3 选**同一个 CatalogController 加 method**（保持 catalog 端点集中）。

## 5. 关键设计取舍

- **不可读节点隐藏而非置灰**：UX 更清晰，避免 user 看到一堆锁图标失去方向
- **面包屑不查 READ**：路径是导航元数据，user 知道节点存在不等于能看（进详情才 403/404）
- **树接口一次拿所有节点**：树规模小（万级），全扫 + 内存组树 + 过滤 性能足够；不引入 lazy 加载的 N+1
- **列表接口 4 种 query method 而非动态 Specification**：简单、类型安全、99% 场景覆盖；余 1% 走 `q` 关键字搜索
- **AclRepository 不暴露为公共 API**：catalog 通过 `PermissionChecker.hasRead()` 间接读；保持 permission 模块内部封装
- **M3 不动 M2-B1/B2**：只新增 `KnowledgeQueryService` + `CatalogController` 3 个 method
- **M3 不实现知识搜索/标签/ES**：留给 M3+
