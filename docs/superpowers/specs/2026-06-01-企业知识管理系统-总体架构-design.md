# 企业知识管理系统 · 总体架构设计

- 日期：2026-06-01
- 类型：总体架构 spec（跨子系统骨架，后续每个里程碑各自再出子系统 spec + 实现计划）
- 状态：已评审通过

## 0. 背景与范围

构建企业级知识管理系统，包含 6 个相对独立的子系统：

1. 文档处理与在线编辑（Word/Excel/PPT/Markdown/TXT 上传 + 富文本在线编辑）
2. 版本管理（历史版本、版本对比、回滚）
3. 知识地图（目录树、知识列表、知识详情）
4. 权限管理（多租户隔离、按组织架构的目录隔离、读/写权限分离，含单知识粒度）
5. 知识审核管理
6. 知识订阅 API（下游实时订阅 + 增量拉取：新增/更新/删除/版本变化）

### 已确定的关键参数

| 维度 | 决策 |
|------|------|
| 技术栈 | Java / Spring 生态（Spring Boot + Spring Modulith） |
| 推进方式 | 整体架构先行，再逐子系统迭代 |
| 多租户隔离 | 共享库 + `tenant_id` 逻辑隔离（预留分库演进路径） |
| 在线编辑 | 单人编辑 + 编辑锁（非实时协同） |
| 订阅机制 | 事务性发件箱（Outbox，真相源，支持增量拉取/重放）+ 作为生产者投递到**已有 Kafka 集群**做实时推送 |
| 架构风格 | 模块化单体（Modular Monolith），用 Spring Modulith + ArchUnit 守边界，后期任一模块可独立拆为微服务 |

## 1. 限界上下文与模块依赖

6 个限界上下文（Spring Modulith 模块），依赖方向严格单向（上层依赖下层，下层绝不反向依赖）：

```
┌─────────────────────────────────────────────────────────┐
│                   接入层 (REST API / 网关)                 │
└─────────────────────────────────────────────────────────┘
        │                                          │
┌───────────────┐  ┌──────────────┐  ┌────────────────────┐
│ catalog 知识地图 │  │ review 审核   │  │ subscription 订阅   │  ← 读侧/流程/出口
│ 目录树·列表·详情 │  │ 审核流·状态机  │  │ Outbox·增量API·Kafka│
└───────┬───────┘  └──────┬───────┘  └─────────┬──────────┘
        │                 │                    │
        └────────┬────────┴─────────┬──────────┘
                 ▼                  ▼
        ┌──────────────┐   ┌──────────────┐
        │ document 文档  │   │ version 版本  │   ← 核心实体
        │ 上传·解析·编辑锁│◄──│ 历史·diff·回滚│
        └──────┬───────┘   └──────┬───────┘
               └────────┬─────────┘
                        ▼
              ┌───────────────────┐
              │ permission 权限/租户 │   ← 地基，被所有模块依赖
              │ 多租户·组织·目录ACL  │
              └───────────────────┘
```

### 模块职责边界

| 模块 | 对外接口（被谁调用） | 发出的领域事件 |
|------|---------------------|---------------|
| **permission** | 所有模块的鉴权入口（`PermissionChecker`） | — |
| **document** | catalog/review 读文档；编辑锁服务 | `DocumentCreated/Updated/Deleted` |
| **version** | document 写版本；catalog/review 读历史 | `VersionCreated/RolledBack` |
| **catalog** | 接入层（目录树/列表/详情查询） | — |
| **review** | 接入层（提审/审批） | `KnowledgeApproved/Rejected` |
| **subscription** | 监听上述所有领域事件 → 写 Outbox → 发 Kafka | （对外即 Kafka 消息 + 增量拉取 API） |

**关键规则：** 模块间不直接调用对方的内部类，只通过 ① 暴露的接口（如 `permission.api.PermissionChecker`）和 ② Spring 应用事件（`@ApplicationModuleListener`）通信。subscription 模块是纯消费者，监听全局领域事件，不被任何业务模块依赖——便于将来独立拆出。

## 2. 统一数据模型

设计原则：

- **每张业务表都带 `tenant_id`**（联合索引首列，逻辑隔离的强制约束）。
- 知识内容与原始文件分离存储：DB 存元数据 + 富文本，对象存储（OSS/MinIO）存原始 Office 文件。
- 知识内容统一收敛到富文本层：Office 上传即转 HTML/JSON 存入 `content_richtext`，让在线编辑、版本 diff、订阅 payload 都基于同一种表示。
- 软删除（`status=DELETED`）而非物理删，保证 `DELETED` 订阅事件可发、审计可追溯。

### permission 模块（地基）

```
tenant          (id, name, status, created_at)
org_unit        (id, tenant_id, parent_id, name, path)          -- 组织架构树，path 物化路径如 /1/4/9/
app_user        (id, tenant_id, username, display_name, status)
user_org        (id, tenant_id, user_id, org_unit_id)           -- 用户∈组织(可多)
acl             (id, tenant_id, resource_type, resource_id,     -- resource=catalog_node（含叶子=单知识）
                 subject_type, subject_id,                      -- subject=org_unit 或 user
                 permission,                                    -- READ | WRITE
                 effect)                                        -- GRANT | DENY（就近优先，见第 4 节）
```

> 权限判定：沿目录树向上找命中规则，就近优先、DENY 覆盖 GRANT、WRITE 蕴含 READ。详见第 4 节。

### catalog + document + version 模块（核心实体）

```
catalog_node    (id, tenant_id, parent_id, name, path, sort,    -- 知识目录树
                 node_type,                                     -- FOLDER | KNOWLEDGE
                 private)                                        -- 可选：断继承标志（后续迭代，默认 false）
knowledge       (id, tenant_id, catalog_node_id, title,         -- 一条"知识"= 一个逻辑文档
                 doc_type,                                      -- WORD|EXCEL|PPT|MARKDOWN|TXT|RICHTEXT
                 status,                                        -- DRAFT|UNDER_REVIEW|PUBLISHED|ARCHIVED|DELETED
                 current_version_id, created_by, updated_at)
knowledge_version (id, tenant_id, knowledge_id, version_no,     -- 每次保存/审核通过 → 新版本
                 content_richtext,                              -- 统一富文本(HTML/JSON)，在线编辑与diff基准
                 original_file_key, file_format,                -- OSS 中原始文件引用
                 change_type,                                   -- CREATE|UPDATE|ROLLBACK
                 parent_version_id, editor_id, created_at,
                 comment)
edit_lock       (id, tenant_id, knowledge_id UNIQUE, holder_id, -- 单人编辑锁
                 acquired_at, expires_at)                       -- 超时自动释放 + 可抢锁
```

> **回滚**不删历史：把目标版本内容复制为一个 `change_type=ROLLBACK` 的新版本，链路可追溯。
> **版本对比**：基于 `content_richtext` 做结构化 diff；Office 原文件转 HTML 后入 `content_richtext`，对比统一在富文本层。

### review 模块（流程）

```
review_request  (id, tenant_id, knowledge_id, version_id,       -- 提审一个具体版本
                 status,                                         -- PENDING|APPROVED|REJECTED|WITHDRAWN
                 submitter_id, reviewer_id, decided_at, opinion)
```

> 审核通过 → `knowledge.status=PUBLISHED` 且 `current_version_id` 指向该版本 → 触发领域事件。

### subscription 模块（出口 · Outbox）

```
outbox_event    (id BIGSERIAL,                                  -- 全局自增 = 拉取游标(cursor)
                 tenant_id, knowledge_id, version_id,
                 event_type,                                    -- KNOWLEDGE_CREATED|UPDATED|DELETED|VERSION_CHANGED
                 payload_json, occurred_at,
                 published_to_mq BOOLEAN)                        -- Kafka 投递标记(发件箱轮询/CDC)
subscriber      (id, tenant_id, name, last_acked_cursor)        -- 下游注册 + 增量拉取断点
```

> **真相源 = `outbox_event` 表**：与业务写操作在同一本地事务内插入（事务性发件箱），保证不丢。
> 轮询器（或 Debezium CDC）扫 `published_to_mq=false` 投递到已有 Kafka 集群 → 实时推送；
> 下游也可调 `GET /events?after_cursor=N` 走增量拉取/重放（自增 id 即游标，天然有序幂等）。

## 3. 变更事件流

### 端到端时序（以"编辑后提审并通过"为例）

```
编辑者保存          审核通过                        下游消费
   │                  │                              │
   ▼                  ▼                              │
┌──────────────────────────────────────────┐        │
│  一个本地数据库事务 (ACID)                   │        │
│  ① knowledge_version 插入新版本             │        │
│  ② knowledge.current_version_id / status   │        │
│  ③ outbox_event 插入 (VERSION_CHANGED)      │ ◄── 业务写 + 事件写同事务，全成功或全回滚
└──────────────────────────────────────────┘        │
                   │ 事务提交                          │
                   ▼                                  │
   ┌───────────────────────────────┐                 │
   │ Outbox 轮询器 / Debezium CDC    │                 │
   │ 扫 published_to_mq=false        │                 │
   └───────────────┬───────────────┘                 │
                   ▼                                  │
        ┌──────────────────────┐                      │
        │   已有 Kafka 集群       │  实时推送 ───────────►│ A. 订阅 topic 实时消费
        │ topic: knowledge.events│                      │
        └──────────────────────┘                      │
                                                       │
        GET /api/events?after_cursor=N  ◄──────────────│ B. 增量拉取/断点重放
```

### 两条投递路径，一个真相源

| 路径 | 机制 | 适用下游 | 语义保证 |
|------|------|---------|---------|
| **A 实时推送** | Outbox → Kafka `knowledge.events` | 要求低延迟的下游 | 至少一次；下游按 `event.id` 幂等去重 |
| **B 增量拉取** | `GET /events?after_cursor=N&limit=` | 重启/补数/对账的下游 | 自增游标有序，可重放、断点续传 |

> 两条路径读同一张 `outbox_event` 表——Kafka 只是它的实时投影。即使 Kafka 整体不可用，下游仍能靠拉取 API 不丢数据。

### 领域事件 → Outbox 的映射

各业务模块只发进程内 Spring 领域事件，由 subscription 模块统一 `@ApplicationModuleListener` 落 Outbox（同一事务内）：

| 业务动作 | 进程内领域事件 | Outbox event_type |
|---------|--------------|-------------------|
| 新建知识并发布 | `KnowledgeApproved`(首版) | `KNOWLEDGE_CREATED` |
| 编辑后审核通过 | `VersionCreated` + `KnowledgeApproved` | `VERSION_CHANGED` |
| 软删除知识 | `DocumentDeleted` | `KNOWLEDGE_DELETED` |
| 回滚到历史版本 | `VersionRolledBack` | `VERSION_CHANGED` |

> **草稿/编辑中不发外部事件**——只有审核通过（PUBLISHED）的变更才进 Outbox。下游看到的永远是"已发布的知识"，审核中的脏数据不外泄。

### event payload（Kafka 消息 / 拉取 API 返回体一致）

```json
{
  "cursor": 10234, "tenantId": "...", "eventType": "VERSION_CHANGED",
  "knowledgeId": "...", "versionId": "...", "versionNo": 7,
  "catalogPath": "/产品/接口规范", "title": "...",
  "docType": "MARKDOWN", "occurredAt": "2026-06-01T...",
  "contentUrl": "/api/knowledge/{id}/versions/7/content"
}
```

> payload 只带元数据 + 内容指针，不塞大正文——避免 Kafka 消息过大，下游按需取。

### 关键取舍

- **事务性发件箱**而非"先写库再发 MQ"：后者在两步之间宕机会丢事件或发空事件，前者用一个本地事务彻底消除该窗口。
- **未发布内容不出库**：以审核通过作为对外可见的唯一闸门，订阅契约简单清晰。

## 4. 权限模型

同时满足三层要求：① 多租户隔离 ② 按组织架构的目录隔离 ③ 读/写权限分离（含单知识粒度）。

### 三层鉴权

```
请求 → [第①层 租户隔离] → [第②层 目录/知识 ACL] → [第③层 读/写区分] → 放行/拒绝
```

**第 ① 层 · 租户隔离（强制、自动、不可绕过）**

- 登录后 `tenant_id` 进入 `TenantContext`（ThreadLocal / 请求作用域）。
- 数据访问层自动注入 `tenant_id` 条件——用 MyBatis 拦截器或 Hibernate `@Filter`/`@TenantId` 全局加 `WHERE tenant_id=?`。
- 开发者写 SQL 时不需要、也不能手动管租户过滤，由框架强制，杜绝越租户漏查。这是共享库方案的安全命门。

**第 ② 层 · 目录 / 知识 ACL（按组织架构隔离，支持单知识粒度）**

权限挂在 `catalog_node` 上（叶子节点即单条知识），沿树向下继承：

```
catalog_node 树            acl 授权                  生效范围
/产品              ← org:产品部 READ GRANT      产品部对 /产品 及其所有子目录可读
  /接口规范         ← org:架构组 WRITE GRANT     架构组对此子树可写(且READ)
  /会议纪要         ← user:张三 WRITE GRANT      张三对此子树可写
    薪酬调整纪要(叶) ← org:全员 READ DENY          这一条知识对"非HR"不可见(就近覆盖上层GRANT)
                   ← org:HR READ GRANT
```

判定算法（对某 user 访问某 catalog_node）：

```
1. 求 user 的主体集合 = { user 自身 } ∪ { user 所属 org_unit 及其所有祖先org }
2. 从目标 node 沿 parent_id 向上（叶子→根）逐级扫命中该主体集合的 acl 记录
3. 同一(主体,权限)以"更靠近叶子"的规则为准；该权限的有效 effect = DENY 则拒绝，= GRANT 则允许
4. 全程无命中 → 默认拒绝
5. WRITE 蕴含 READ：在以上判定得到 WRITE=GRANT 时同时具备 READ
```

> **物化路径加速**：`catalog_node.path`（如 `/1/4/9/`）和 `org_unit.path` 让"取所有祖先"一次查询完成，避免递归。
> **单知识粒度**：
> - *额外授权（加人）*：把 ACL 挂到该知识叶子节点，自动并入向上遍历，零额外成本。
> - *更私密（减人）*：用 `effect=DENY` 就近覆盖上层 GRANT；子目录/叶子可再 GRANT 回来。
> - *完全独立白名单（可选后续）*：`catalog_node.private=true` 断继承，只认该节点自身 ACL，是 DENY 的快捷特例。

**第 ③ 层 · 读/写分离（动作映射到所需权限）**

| 动作 | 需要的权限 |
|------|-----------|
| 查看目录树/列表/知识详情（catalog） | READ |
| 上传/在线编辑/获取编辑锁/提审（document, review 提交侧） | WRITE |
| 审核通过/驳回（review 审批侧） | WRITE + 审核者角色 |
| 回滚版本 | WRITE |

> 审核需要"写权限 + 是被指派的审核者"双条件——避免有写权限的人自审自过。审核者由 `review_request.reviewer_id` 指派，或按目录配置审核者组（后续迭代）。

### 统一入口：PermissionChecker

permission 模块只暴露一个接口给所有上层模块，杜绝各模块各写一套判定：

```java
public interface PermissionChecker {
    void check(Long userId, Long catalogNodeId, Permission required); // 不通过抛 AccessDeniedException
    boolean has(Long userId, Long catalogNodeId, Permission required);
}
```

接入层用 Spring Security 方法注解 + 自定义表达式串起来，例如 `@PreAuthorize("@perm.has(...)")`，业务代码里不散落 if-else 鉴权。

### 关键取舍

- **默认拒绝**（无规则命中即无权），企业知识库安全基线。
- 权限挂目录/叶子、靠继承，授权点少、可维护，符合"按组织架构的目录隔离"原意，同时覆盖单知识粒度。
- **就近优先**而非"全局 DENY 优先"：让子目录/单知识能重新授权回来，符合"越靠近资源的规则越权威"的直觉。
- 租户过滤下沉到框架层强制执行，不依赖开发者自觉——共享库多租户唯一可靠的做法。

## 5. 构建顺序与里程碑

按依赖方向"从地基往上"逐块交付，每个里程碑都是可独立验证的纵切片。

```
M0 工程骨架 ──► M1 权限地基 ──► M2 文档+版本 ──► M3 知识地图 ──► M4 审核 ──► M5 订阅出口
   (脚手架)      (地基)          (核心主线)        (读侧)         (闸门)       (出口)
```

| 里程碑 | 范围 | 完成判据（可演示） | 关键风险 |
|--------|------|-------------------|---------|
| **M0 工程骨架** | Spring Boot + Spring Modulith 6 模块空壳、ArchUnit 守边界、统一异常/返回、`TenantContext` + 框架级租户过滤、OSS 接入、库迁移(Flyway) | 跨模块非法依赖编译期/测试期失败；带 tenant_id 的空 CRUD 跑通 | 边界纪律——一开始就用工具焊死 |
| **M1 权限地基** | tenant/org/user/acl 模型、`PermissionChecker`、三层鉴权、`effect` 就近优先算法、目录树 CRUD | 不同租户互不可见；目录/单知识 ACL 的"加人/减人/读写分离"可演示 | 租户过滤不可绕过；判定算法正确性（重点测试） |
| **M2 文档+版本** | 5 种格式上传→转富文本入库、在线富文本编辑、编辑锁、版本生成/历史/diff/回滚 | 上传 Word→在线编辑→存多版本→对比→回滚全链路 | Office→HTML 转换保真度（最高技术风险，先做转换 PoC） |
| **M3 知识地图** | 目录树/知识列表/详情查询，全部经权限过滤 | 按登录用户权限渲染可见的树与详情 | 列表/树的权限过滤性能（物化路径 + 分页） |
| **M4 审核** | 提审→指派审核者→通过/驳回状态机、发布闸门、审核者双条件 | 草稿提审、审批通过后才 PUBLISHED、驳回回到草稿 | 状态机与版本/发布的联动一致性 |
| **M5 订阅出口** | Outbox 事务写入、轮询/CDC 投递已有 Kafka、增量拉取 API、游标/重放 | 一次发布同时产生 Kafka 消息 + 可被 `/events?after_cursor` 拉到 | 至少一次语义 + 下游幂等；Outbox 不丢 |

### 推进建议

- **M2 前先做"Office→富文本转换" PoC**：全系统保真度与可行性的最大不确定点，POI / LibreOffice headless / 第三方服务三选一需单独评估。
- 每个里程碑结束都走一遍"设计 → writing-plans 计划 → 实现"的小循环。本份是总体架构 spec，每个 M 再各自出子系统 spec + 实现计划。
- M0 的边界工具（Spring Modulith + ArchUnit）是后期把任一模块独立拆为微服务的保险，不可省。

## 6. 测试策略（贯穿各里程碑）

- **端口-适配器 + local-mock**：数据库与中间件（DB、对象存储、Kafka）一律置于模块内的端口接口之后，每个端口提供生产适配器（JPA/MinIO/Kafka）与内存适配器两套实现。测试分两层：默认快速层用内存适配器、零中间件、可在 AI IDE 直接运行；集成层（`@Tag("integration")`）用 Testcontainers 验证真实接线（Hibernate `@TenantId` 过滤、Flyway、MinIO 等）。`local-mock` profile 排除 DB/中间件自动配置，整套应用可零依赖启动供手动验证。
- **模块边界**：ArchUnit / Spring Modulith `verify()` 在 CI 强制单向依赖。
- **租户隔离**：每个仓储测试都加"跨租户不可见"用例，作为安全回归基线。
- **权限判定**：对就近优先 + DENY 覆盖 + WRITE 蕴含 READ 编写穷举表驱动测试（继承、跨级、加人、减人、断继承）。
- **版本/回滚**：往返测试（创建→编辑→回滚→对比）验证历史不丢、链路可追溯。
- **Outbox 一致性**：在业务事务回滚时断言事件不产生；提交时断言事件产生且可被拉取 API 与 Kafka 同时看到。
